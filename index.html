P.1 — R&D Phase: Samples entered under # to R&D are sent to the R&D team for the number of months defined by Duration, starting from the date entered in P.1 St. (mm/yyyy). Once the P.1 window closes, the total accumulated samples (# to R&D × Duration) are transferred to Foundry in the single month immediately following, marked with an asterisk (*).

P.2 — Split Phase: Samples entered under # Samples are split between R&D and Foundry according to the percentages entered in % to R&D and % to Foundry, for the duration defined by P.2 St. and Duration. Each team's share is shown in their respective calendar row. Each team's share can be overridden independently.

P.3 — Foundry Phase: Samples entered under # Samples go entirely to the Foundry team for the duration defined by P.3 St. and Duration.

Overrides — two highlight colours distinguish where an override originates. Calendar-origin override: any calendar cell edited directly, plus partnerships table cells whose value reflects those calendar edits — % to R&D and % to Foundry highlight when a calendar override exists inside the P.2 window; P.2 Duration and P.1 Duration highlight when calendar edits push outside the expected range; P.3 # Samples and P.3 Duration highlight when a Foundry calendar override exists in the P.3 window. Table-origin override: partnerships table cells typed directly — P.1 Take-on Rate %, P.2 Take-on Rate %, Avg Time (mo.) for Foundry to Biobank, Avg Time (mo.) to Biobank Samples Received from R&D, and % Foundry Workload into Biobank. Clearing any override restores the computed value and removes the highlight.

Avg Time (mo.) for Foundry to Biobank: A per-source-type input above the partnerships table controlling how many months Foundry takes to biobank samples after receiving them. Use the dropdown to select the source type (PDOs, Fresh Samples, Cryo Samples); the number input auto-fills from the uploaded Foundry processing protocol for that source type (Manual Sheet Upload → Processing Protocols → [source] → Foundry tab): the Duration (weeks) values are summed across all rows up to (but not including) the first stage whose name contains "Banking" or "Cryo", then divided by 4 to convert to months and rounded to the nearest whole number. Manually entering a value overrides the auto-fill and highlights the input green. Typing the auto-filled value back clears the override.

Avg Time (mo.) to Biobank Samples Received from R&D: A per-source-type input controlling how many months it takes to biobank samples received from R&D. Click + to add a row for each source type; click × to remove one. Each row has its own source dropdown (PDOs, Fresh Samples, Cryo Samples) and number input. Values auto-fill from the predictive values sheet by matching the column titled Avg time (month) foundry biobanks [source] from R&D (case-insensitive — e.g. Avg time (month) foundry biobanks PDO from R&D matches the PDOs row). Manually entering a value overrides the auto-fill and highlights the input green. Typing the auto-filled value back clears the override.

Rounding: All sample counts are rounded down to the nearest whole number (floor) before display.

Sanity Check — P.2 Calendar Totals: If P.2 R&D or Foundry calendar cells are overridden and their sum across the full P.2 duration no longer equals the expected total (floor(# Samples × % to R&D or % to Foundry) × Duration), the # Samples cell for P.2 in the partnerships table is outlined in crimson. This check only fires when the duration in the partnerships table has not been changed. Clicking the cell opens a memo listing every active error on that cell — each mismatch (R&D, Foundry, sample accounting) is listed separately, and the border thickens when multiple errors are present simultaneously. The outline clears once all offending overrides are corrected or removed.

Sanity Check — P.2 Override Outside Duration: If a P.2 R&D or Foundry calendar cell is overridden in a month that falls outside the P.2 duration window set in the partnerships table — and that month does not belong to another active phase for that deal (P.1 R&D, P.1 Foundry delivery, or P.3) — the Duration cell for P.2 in the partnerships table is outlined in crimson. Clicking the cell opens a memo listing every out-of-bounds month and which team row it belongs to, and prompts you to either extend the P.2 duration or remove the calendar override. If the duration cell already has a phase-conflict outline, the border thickens to signal the combined error.

Sanity Check — Phase Conflicts: Calendar cells are outlined in crimson when any two phase windows overlap in time or are entered out of order. Four windows are tracked per deal: P.1 R&D (start → start + duration), P.1 Foundry delivery (start + duration + delay → + delivery duration), P.2, and P.3. Every pair is checked. Additionally, any phase whose start date falls before the deal's Rec. Start date is flagged. All months belonging to the conflicting window(s) are marked. Note: P.1 Foundry delivery overlapping with P.2 or P.3, and P.2 overlapping with P.3, are not flagged as errors — these sequences are expected by design.

Sanity Check — Sample Accounting: The Sample nb, Samples left column and the entire calendar are outlined in crimson when the calendar total for a deal does not exactly match its target. The calendar total is the sum of four components: blue values in the R&D row for P.1 + blue values in the R&D row for P.2 + magenta direct-to-foundry values in the Foundry row for P.2 + magenta/purple values in the Foundry row for P.3. Two categories are deliberately excluded to avoid double-counting: P.1 Foundry delivery (teal in the Foundry row) is excluded because those samples were already counted when they passed through the R&D row; P.2 R&D→Foundry transfers (teal in the Foundry row) are likewise excluded because they were already counted as blue R&D values in the R&D row. The target is Nb samples remaining to receive for deals sourced from Actuals — Reception, or Nb samples from the Master Database otherwise. Clicking the column header or the calendar while the error is shown displays a memo listing each mismatched deal with its calendar total and target. The error does not fire when no planning data has been entered.

Sort by: Reorders all active deals by the selected column. Blank and N/A values in the sorted column always float to the bottom of the active section regardless of sort direction, separated by a DimGray bar. On Hold and Killed deals are permanently anchored below all active deals regardless of sort selection, separated by a black bar.

Group by: Applies a secondary clustering within the order established by Sort by. Rows that share the same value in the selected column are kept adjacent, with sub-groups ordered A–Z. For example, sorting by Hospital Code A–Z and grouping by Cancer Type will sort deals by hospital code as the primary order, then within each hospital code cluster arrange deals by cancer type alphabetically. Group boundaries within active deals are marked by a gray bar. Blank and N/A values in the group column cluster at the bottom of each sort group.

Take-on Rate %: The percentage of samples that successfully progress from the R&D phase through to Foundry. A value of 90 means 90 out of every 100 samples make it through. Applies to P.1 (R&D → Foundry transfer) and P.2 (R&D → Foundry transfer). Both phases use the same rate for a given deal. When left blank, the rate auto-populates from the Take-on Rate sheet (uploaded under Manual Sheet Upload → Take-on rate): the deal's Cancer type identifies the column and the deal's Source identifies the row, and the value at their intersection is used. Manually entering a value overrides the auto-populated one. The auto-populated source is noted in the cell tooltip.

Biobanked Row — Calculation: The Biobanked row shows when foundry samples are expected to complete processing and be biobanked. Direct (pink/purple) foundry values are shifted forward by the PDO delay and teal R&D-transfer values (P.1 delivery and P.2 R&D→Foundry) are shifted forward by the avg time — both scaled by the % Foundry Monthly Workload into Biobank rate. Clicking a biobanked cell shows a breakdown of how much of that month's total comes from each source. The displayed breakdown figures are each floored independently, so their sum may differ from the cell total (which is the floor of the exact combined value) — for example, 1.7 direct + 1.8 R&D transfer floors to 1 + 1 in the breakdown but to 3 in the cell.

Foundry Cell Colour Override: Right-click any filled cell in the Foundry row to toggle its colour between Foundry magenta and R&D blue. Changing to R&D blue reclassifies those samples as R&D-origin in the Ceiling and Scenario Visualization — they count toward the R&D-coloured share of Foundry throughput and affect the volume-weighted lag calculation. Use this to manually correct the colour when a cell's automatic phase colouring does not match the intended classification.

Current Biobank

All three charts draw exclusively from the Actuals — Biobanked sheet uploaded under Manual Sheet Upload.
By Cancer Type — sums the Nb samples biobanked column, grouped by the Cancer type column. Each slice represents the total number of biobanked samples associated with that cancer type across all studies and sites.
By Source — sums the Nb samples biobanked column, grouped by the Source column. Each slice represents the total number of biobanked samples by collection method or origin type.
Biobanked by Year — sums the Nb samples biobanked YYYY columns (e.g. Nb samples biobanked 2024, 2025, 2026 …), one slice per year. New year columns added to the sheet will be picked up automatically.

Predicted Biobank

Each chart combines two sources:

Actuals (baseline) — the all-time cumulative Nb samples biobanked column from the Actuals — Biobanked upload, summed per cancer type and source. The By Year chart sums the Nb samples biobanked YYYY columns per year.

Projected (selected year) — the Scenario Builder calendar's biobanked row for each active, non-filtered deal in the selected year. Each deal's projection factors in phase timings, take-on rates, delays to biobank, and any calendar overrides. Scenario Builder filters apply. For the By Year chart, projected totals are added for every year in the calendar, not just the selected year.

The two are summed per category to give the expected cumulative total at end of the selected year. If only one source is available the chart renders with what is present.
